RATAN TRADE-CRAFT TOOLKIT // RED-TEAM INFRASTRUCTURE

C2 frameworks: what replaced Cobalt Strike, and what actually catches it.

Cobalt Strike stopped being the default answer years ago. Licence cost, signature maturity and a well-documented detection ecosystem pushed serious teams toward open-source command-and-control frameworks — Sliver, Mythic, Merlin, AdaptixC2 — while Havoc, the one everybody recommended in 2023, has since been archived by its maintainer.

This page is written for two readers at once: the operator who has to pick and run infrastructure without burning the engagement, and the defender who has to detect it afterwards. Same systems, same telemetry, two viewpoints.

Read this before you install anything.
  • A C2 framework is not a hacking tool you point at a target. It is infrastructure you build inside a lab you own, or inside an engagement whose written authorisation names the assets, the window and the abort path.
  • Running implants on systems you do not own is a criminal offence in India under the IT Act 2000 (§43, §66), and in most other jurisdictions under computer-misuse statutes. Cost and career damage are real.
  • Nothing on this page is an instruction to target anyone. It documents architecture, selection criteria and detection — the parts that make you employable as a red teamer.
  • Never test with production credentials or customer data. Use a scratch account in an isolated lab.

What a C2 framework actually is

Strip away the branding and every framework — commercial or open source — is the same four moving parts. If you understand these, you can evaluate any tool in ten minutes, and you can also explain to a defender where to put the sensor.

01 // TEAMSERVER

Control plane

The service operators connect to. Holds task queues, session state, loot and multi-operator accounts. Everything valuable sits here, which is exactly why it never faces the internet in a mature build.

02 // LISTENER

The front door

A bound port speaking HTTP/S, DNS, mTLS, SMB or WireGuard. Listener configuration — not implant quality — is what determines whether the network sees you. Host header, TLS fingerprint, URI layout, response shaping.

03 // IMPLANT / AGENT

Where it runs

Beacon (Cobalt Strike), Sliver implant, Merlin agent, Mythic payload, Adaptix beacon. Sleep interval, jitter and per-command execution each leave a separate forensic trail. Sleep masks, indirect syscalls and in-memory loading are evasion layers, not invisibility.

04 // REDIRECTOR

The disposable layer

A cheap VPS, CDN or cloud function that receives operator traffic and forwards it to the teamserver. Protected by a host allowlist or mTLS client certificate. When it burns, you rebuild it in twenty minutes and your operation survives.

OPERATOR→REDIRECTOR (allowlisted)→TEAMSERVER (private)→LISTENER→IMPLANT→VICTIM HOST

The redirector is the single highest-value design decision in red-team infrastructure. It decouples your teamserver's identity from what the target sees, and it converts a career-ending incident into a ten-minute rebuild.

Which one should you actually pick?

There is no best framework, only a best fit for the constraint you are actually under. Answer the question that matches your situation.

"My budget is zero."

Sliver as the primary, Merlin or AdaptixC2 as a second option for variation. Sliver has the largest active community among the free options, which means more community profiles, more write-ups and — usefully — more detectors familiar with it. Mythic if you have the patience to deploy it properly and want a platform rather than a tool.

"I am testing mature EDR."

No framework solves EDR on its own. What works is implant-plus-profile discipline: an encrypted channel whose TLS fingerprint matches real browser traffic, a URI layout that looks like the application you are pretending to be, sane sleep and jitter, and egress through a redirector that is not a fresh VPS on a flagged ASN. Pick the framework whose profile syntax you can actually customise — Cobalt Strike and Mythic lead here. Whatever you choose, expect behavioural detection: cross-process memory access and LSASS handles get caught regardless of C2 branding.

"I need to test on Linux and macOS too."

Sliver or Merlin. Both ship genuine multi-platform implants rather than bolting a Linux agent onto a Windows-first design. Cobalt Strike covers Linux but its centre of gravity is Windows.

"I am a defender, not an operator."

You do not need to run C2 in production to learn it — and you should not. Stand up the isolated lab further down this page, run one framework at a time, and capture your own telemetry. Then walk to the detection playbook. Defenders who have felt a beacon schedule on their own network write materially better rules than defenders who have only read a vendor blog.

"I want to learn how beacons work."

NimPlant for readable, educational design, then read Sliver's Go source. Reading an implant's sleep-jitter loop in source code teaches you more about beacon detection than any article — you will see exactly which timestamps, packet sizes and TLS handshakes it cannot hide.

"My client wants a purple-team outcome."

Optimise for measurability, not stealth. Empire plus Atomic Red Team gives many small, attributable technique tests. Pair every executed technique with the ATT&CK ID so the report writes itself — the mapper on this site generates that plan and gap list for you.

How the infrastructure is supposed to be built

This is architecture, not a runbook. Every framework's own documentation covers installation; what they under-document is the discipline that keeps an engagement from becoming an incident.

  1. Registration and hosting hygiene

    Domains registered with a privacy-respecting registrar, aged before use, categorised as business or technology rather than "newly registered", and hosted on ASNs that are not already burned by every other test on the internet. Reputation is purchased in weeks, not minutes.

  2. Redirector layer, always

    Operator traffic reaches a cheap VPS, CDN distribution or cloud function. That layer forwards to the teamserver only when the request carries the expected Host header, URI path or a mutually authenticated client certificate. Everything else gets a benign page. A direct-to-teamserver operation is one blue-team query away from being over.

  3. Teamserver never faces the internet

    Firewall rules allow the redirector and the operators' egress IPs, nothing else. Operators connect over a management VPN. Multi-operator deployments get named accounts so the audit log means something after the engagement.

  4. Traffic shaping matched to the cover story

    If the operation pretends to be a corporate web application, the TLS fingerprint, certificate chain, header order, URI vocabulary and response-size distribution should resemble that application. Malleable C2 profiles (Cobalt Strike and Empire), Mythic's profile system and Sliver's HTTP configuration all expose this — but only if you configure them instead of pressing default.

  5. Sleep, jitter and beacon economics

    Long sleep with high jitter defeats interval analysis that a naive 60-second beacon cannot. Note the trade-off honestly: quiet beacons slow the operation, and impatient operators kill more engagements by abandoning the profile than defenders ever do.

  6. Log and evidence discipline

    Operators log every command with a timestamp and a justification. Not for the client — for you, when someone asks in month three why a particular subnet was touched. Engagement evidence lives on an encrypted volume that you can hand over or destroy on schedule.

  7. Teardown plan written before build

    Which implants get removed, which persistence is reverted, which redirectors get destroyed, and what happens to acquired credentials. If you have not written the teardown, you have not finished planning the engagement.

The uncomfortable professional truth: infrastructure quality is the difference between a red team and a liability. The framework you pick is a footnote; the redirector design, the profile discipline and the teardown plan are the actual skill. Interviewers ask about those, not about which tool was in your terminal.

Detection playbook — the defender's side

Every framework above leaks in the same categories of telemetry. This is what to build, and roughly what it catches. All of these map into TA0011 Command and Control and TA0005 Stealth in the ATT&CK v19 restructure.

LAYER 01 // NETWORK

Beacon interval analysis

Log every outbound connection with size and timestamp; look for regularity, not volume. A connection that fires every 62 seconds with 8% variance for six hours is a machine talking to a scheduler, not a human using a website. Tools: Zeek connection logs shipped to a SIEM, RITA, or a simple hourly aggregation you write yourself.

Catches poorly configured default beacons — still the majority of what you will actually encounter.
LAYER 02 // TLS

TLS and JA3/JA4 fingerprinting

Capture JA3/JA4 client fingerprints on egress. Go-based implants (Sliver, Merlin) and Cobalt Strike's beacon each produce characteristic fingerprints, and a self-signed or oddly-chained certificate is a strong secondary signal. Alert when an endpoint process that is not a browser produces a browser's fingerprint, or when a browser produces a non-browser's.

Weakness rotated profiles and CDN-fronted infrastructure blunt it — treat it as one input, not a verdict.
LAYER 03 // DNS

DNS anomaly detection

High-entropy subdomains, NXDOMAIN bursts, long TXT answers, unusual record types and consistent query lengths. DNS-over-HTTPS belongs here too — encrypting resolver traffic moves the problem, it does not delete the metadata. Baseline per-host query patterns first or you will drown in false positives.

Catches DNS tunnelling and domain-generation-algorithm beaconing well (ATT&CK T1071.004, T1568.002).
LAYER 04 // ENDPOINT

Process and memory behaviour

Cross-process memory access, remote thread creation, handles to lsass.exe, unsigned modules loading into signed processes, and process lineage that makes no sense (a spreadsheet spawning a shell). This layer is C2-agnostic: it catches the post-exploitation behaviour regardless of which framework produced it.

Strongest layer because it does not depend on attacker branding.
LAYER 05 // IDENTITY

Authentication and session anomalies

New source-to-destination pairs, NTLM authentication with no preceding interactive logon (pass-the-hash), Kerberoasting-shaped service-ticket requests in bulk, and session-cookie reuse from unfamiliar devices. Modern intrusions lean on valid accounts, so identity telemetry frequently outperforms network detection.

Maps to TA0006 Credential Access, TA0008 Lateral Movement.
LAYER 06 // EGRESS

Egress policy as a control

Default-deny outbound by destination class: known-good SaaS, approved update infrastructure, deny everything else with an exception process. This is unfashionable because it is inconvenient, and it is also the single highest-leverage control against C2, because an implant that cannot reach its redirector is just a process. Log the denials — the denial list is a free hunt feed.

Design goal raise the attacker's cost above the engagement budget.

A detection rule you can write today

One concrete example of the discipline that matters more than tool choice: a hypothesis, the telemetry it needs, and the tuning that keeps it alive in production.

HYPOTHESIS

"We would see a non-browser process holding a long, periodic TLS session to a newly-seen domain."

Write it as one sentence first. If you cannot state the hypothesis, you are about to write a rule nobody can triage.

  • Telemetry: Zeek ssl.log and conn.log, joined to endpoint process-creation logs on host and approximate time.
  • Logic: same host, same destination, ≥5 connections, ≥30 minutes apart-by-consistency, standard deviation of intervals under 15% of the mean, JA3 not in the known-browser set, destination domain first seen in the last 30 days.
  • Enrichment: domain age, ASN reputation, certificate issuer, whether any other host in the estate has contacted it.
TUNING

Why most versions of this rule die in week two

Software updaters, telemetry agents and SaaS keep-alives all beacon. The rule only survives if you tune before you enable it:

  • Allowlist by process and publisher, never by domain alone.
  • Require the newly-seen-domain condition — age is the cheapest precision you will ever get.
  • Send first as an enrichment-only alert into a weekly review, then promote to paging once noise is measured.
  • Attach a triage runbook: what is this process, who owns this host, is the destination in our vendor inventory. A rule with no runbook becomes an ignored rule.

Building the home lab (safely)

Everything on this page assumes a lab you fully control. The design goal is a network with no route to anything you care about — including your own house.

  1. Isolate at the hypervisor, not at the router

    Create a host-only or internal virtual switch with no NAT and no bridged adapter. Three VMs: an attacker box, a Windows target, and a Linux target. If you can reach the internet from a lab VM, your lab is not isolated — and neither is your home network.

  2. Snapshot before every run

    Revert-to-snapshot is your rollback plan and your repeatability. It is also how you practise honestly: same starting conditions, comparable results.

  3. Deploy a logging target, not just a victim

    Add a fourth VM running Zeek or Suricata plus an index. Capturing your own traffic and reading it is where the learning happens — the moment you see your own beacon pattern in a connection log, you understand detection permanently.

  4. Stand up the target application range

    Deliberately vulnerable targets such as the OWASP Juice Shop or a DVWA instance give you a realistic landing point without touching anything real. Keep them off any public interface.

  5. Load one framework at a time

    Run Sliver for a week, capture telemetry, write what you saw. Then Merlin. Then a second. Comparing fingerprints across frameworks is the skill that transfers to a real engagement — and to a defensive interview.

  6. Practise the boring parts

    Build a redirector and watch the allowlist reject a wrong Host header. Configure a profile and diff the TLS fingerprint before and after. Practise teardown until it is muscle memory. This is the work nobody demos and everybody is hired for.

  7. Document, then delete

    Write up what each technique looked like in telemetry, mapped to ATT&CK IDs. Then destroy the lab artefacts. Your notes are the asset; the running implants are the liability.

Hard rule for the lab: no production credentials, no customer data, no corporate laptop, no VPN to a real employer's network, and no bridged networking. If any one of those is present, stop and rebuild. See Acceptable Use.

Common questions

Is using C2 frameworks legal?

The software is legal to download, study and run on systems you own. Using it against a system without written authorisation is an offence in essentially every jurisdiction. In India the relevant provisions are §43 and §66 of the IT Act 2000, with aggravated provisions where critical infrastructure is involved. "I was only testing" is not a defence — the authorisation document is.

Why did everybody stop recommending Havoc?

Because its repository was archived in December 2025 and stopped receiving updates. Archive status is not a moral judgement on the tool — Havoc's syscall work influenced a lot of what came after. It is a maintenance fact: unmaintained security tooling accretes bugs, drifts from current detection research, and gives you no route to a fix when the framework itself becomes the finding in a client report.

Should I learn Cobalt Strike if I cannot afford it?

Learn the concepts, not the licence. Malleable profile logic, BOF-style post-exploitation, jump and pivot modelling, and beacon sleep/jitter economics all exist in the open-source frameworks here. If an employer needs Cobalt Strike specifically, they will pay for it — the skill they are hiring is the tradecraft around it, and that transfers directly.

Which framework is hardest to detect?

That question has no stable answer, and treating it as the goal is how engagements go wrong. Detection resistance is a property of your configuration and infrastructure, not the product logo: profile quality, TLS fingerprint, redirector reputation, egress path, and how much post-exploitation you do on disk. The same Sliver binary with a thoughtful profile is far harder to catch than a badly configured deployment of anything else.

I am preparing for a red-team interview. What should I actually study?

Redirection and OPSEC design; the difference between evasion and detection; how you would explain a technique's telemetry to a blue team; and how you write a report that changes behaviour. Interviewers can tell within two questions whether someone has only watched tool demos. Being able to say "here is what this looks like in Zeek and here is the rule I wrote" separates candidates faster than any certification.

Can you help me use one of these against a target?

Against a system you own, or one covered by written authorisation, yes — I will help with architecture, profile reasoning, reporting and detection. Against anything else, no, and please do not ask: it is the one line that turns training into a criminal matter.
