RATAN OS ADVANCED EDITION // ROADMAP & BUILD SYSTEM

Build the lab OS you actually need.

RATAN OS is a Debian-based live system for authorised security work: an offline AI assistant that never phones home, curated tool collections, and isolated lab profiles you can boot without touching a production network. This page is the engineering roadmap and an interactive planner — choose the modules you want for your own build and get a reproducible manifest, a size estimate and a dependency check.

Architecture

Six layers, each independently verifiable. If a layer cannot be inspected and rebuilt, it does not belong in a security distribution — including the AI parts.

LAYER 6
Report & evidence

Per-technique evidence capture, timestamped operator logs, and output that maps directly to the ATT&CK coverage report: airt report --format=sarif, attack-map export.

LAYER 5
Lab profiles

Declarative YAML describing an isolated range — vulnerable web target, domain controller and workstation pair, or an AI/LLM endpoint with the AIRT scanner pointed at it. Booted on an internal virtual switch with egress denied by default.

LAYER 4
Tool collections

Curated apt and source-built sets, version-pinned and provenance-checked. Each collection is documented as a shelf with a stated purpose, which keeps the image auditable and keeps users from installing the entire internet.

LAYER 3
Offline AI runtime

llama.cpp compiled CPU-only with a quantised GGUF model, served on loopback and proxied to a local browser UI. No telemetry, no outbound calls, no API key — the design constraint is that inference works on a plane with Wi-Fi off.

LAYER 2
Package layer

Debian Trixie base with a signed local repository for the project's own packages, so boot-time and post-boot installs are both verifiable. Unsigned external repositories defeat the point of a trust centre.

LAYER 1
Base system

Debian live-build with XFCE, a reproducible build script committed to the repository, and a published SBOM once the v2.0.0 pipeline lands.

Design rule that shapes everything above: the AI assistant is local by construction, not by configuration. A security distribution that quietly ships your notes to a vendor API has failed at the first requirement. If a feature cannot work offline, it does not ship.

Lab profiles

The point of a hacking-focused OS is not a bigger toolbox — it is a smaller distance between "I read about this technique" and "I watched it happen in telemetry." Each profile is a self-contained range you can boot, break and destroy.

PROFILE 01

Web & API range

A deliberately vulnerable application stack plus an API target, instrumented so you see both the exploitation and the server-side evidence.

  • Vulnerable app + API target
  • Reverse proxy and WAF in front for bypass practice
  • Access and error logs shipped to a local index
  • Maps to OWASP Top 10 and API Top 10 categories
PROFILE 02

Active Directory range

Domain controller plus two member hosts on an isolated switch. Identity-centric intrusion practice with real audit logs to read.

  • Domain + member server topology
  • Kerberos and delegation practice scenarios
  • Windows security event collection and search
  • Detection review as the second half of every exercise
PROFILE 03

AI / LLM red-team range

A local model endpoint wired to the AIRT scanner from this site, so prompt-injection and boundary testing runs entirely offline.

  • Local inference endpoint, no cloud dependency
  • AIRT probes with OWASP LLM Top-10 mapping
  • Deterministic scoring with canary-token evidence
  • SARIF and HTML reports for review sessions
PROFILE 04

C2 sandbox range

For studying command-and-control architecture and — more importantly — what it looks like in network telemetry. Read the framing on the C2 frameworks page before using it.

  • Internal-switch-only topology, egress denied
  • Connection and TLS metadata capture
  • Beacon-interval and fingerprint analysis exercises
  • Redirector allowlisting practice
PROFILE 05

Forensics & response range

Pre-captured artefacts from a completed exercise, so you can practise investigation without generating an incident first.

  • Disk and memory captures with a known timeline
  • Log corpus with injected attacker activity
  • Timeline reconstruction and hypothesis testing
  • Report against a written scenario
PROFILE 06

Purple-team range

The one that produces the most employable skill: run the technique, then measure your own detection of it, in one loop.

  • Technique execution linked to ATT&CK IDs
  • Local telemetry stack for detection writing
  • Coverage export into the ATT&CK mapper
  • Gap report generation for a written deliverable

Trust engineering

A security distribution is judged by what it can prove about itself. These are the commitments that separate a hobby ISO from something a professional can boot on a work laptop.

01 // INTEGRITY

Published checksums

Every release ships SHA-256 hashes alongside the image, generated from the build output rather than typed by hand. Verify before boot — a corrupted live image is an unreliable lab.

02 // AUTHENTICITY

GPG-signed releases

Release artefacts and the project's own package repository are signed with a published, documented key. You should be able to prove that what you downloaded is what was built, without trusting the download page.

03 // REPRODUCIBILITY

Build script in the open

The live-build configuration lives in the repository. Anyone can rebuild the image and compare results — the strongest available answer to "what is actually inside this ISO?"

04 // TRANSPARENCY

SBOM per release

Once the v2.0.0 pipeline ships, every release carries a machine-readable software bill of materials, so an organisation can audit exactly which components are present and at which versions.

05 // PRIVACY

No telemetry, by design

The assistant binds to loopback, the image does not require an account, and nothing is uploaded. This is architectural, not a policy promise you have to take on faith.

06 // BOUNDARIES

Documented operating limits

The project states plainly what the image is for and what it must never be used on: no production credentials, no regulated data, no critical systems. Read the acceptable-use and terms pages before deploying it anywhere.

Not security-audited. RATAN OS is a learning and lab platform, not an audited enterprise product, and this page does not claim otherwise. Boot it on hardware you can afford to lose, on networks you are authorised to change, and never as your only defence against anything.

From a roadmap item to a release

How a module here becomes something you can download. This is the pipeline the v1.4.0 lab-profile and signed-repository work will pass through.

01 // SCOPEA module earns its place only if it serves a stated learning outcome. No outcome, no package.
02 // PINEvery dependency is version-pinned with provenance recorded, so builds are repeatable months later.
03 // BUILDDebian live-build runs from the committed configuration; the image is produced by script, never assembled by hand.
04 // TESTBoot in QEMU BIOS, confirm the AI runtime answers offline, confirm lab profiles cannot reach the internet.
05 // SIGN & PUBLISHHash, sign, publish with a verification guide and an honest statement of what the build does not do.
